# 审核留痕改造（2026-11-14）

## 为什么要改

改造前，人工审核结果是**覆盖写**的：

```python
review = existing.get(key)          # 一个任务一个字段只有一行
review.final_value = field.final    # 直接盖掉上一次
review.change_reason = ...
```

同一个字段被改三次，只留最后一次的 `change_reason`。"谁在何时把 A 改成 B、当时给的理由是什么"——永久丢失。对一个要给业务方交数据的审核工具来说，这一半价值就没了。

另外，详情页的"审核历史"是**从当前状态倒推**出来的列表（`for review in task.human_reviews`），不是真实事件流，也没有"改前值 → 改后值"。前端还会在保存成功后本地拼一条 `{who: "当前经理", when: now}` 塞进去，连时间都是浏览器本地时钟。

更麻烦的是 `reviewer`：前端从不传，后端一律兜底成字符串 `"当前经理"`。多人协作时完全无法归责。

## 改成了什么

新增 `review_events` 表（append-only，只插入不更新），`HumanReview` 降级为**当前值缓存**——仍然按 `(task_id, field_name)` 唯一，负责快速读当前状态。

```
review_events
  id / task_id / event_type / field_name
  value_before / value_after / reason / reviewer
  created_at
  index (task_id, id)
```

### 写入规则（这块决定日志好不好用）

| 情况 | 事件 | 说明 |
|---|---|---|
| 字段值变了 | `field_change` | 带 `value_before` / `value_after` |
| 值没变、只有修改原因变了 | `field_reason` | 单独一种类型，不和值变更混在一起 |
| 点"保存草稿" | `save` | `value_after` 存 `已确认 x/47`，即使一个字段都没改也记 |
| 点"提交完成审核" | `submit` | 同上 |
| 升级前的存量记录 | `legacy` | 见下方回填 |

**为什么不逐字段记录"确认/取消确认"**：那样一次提交就是 47 条噪声，真改动会被埋掉；而 `HumanReview.confirmed` 已经存了每个字段最后一次的确认状态，两次确认之间的反复没有审计价值。会话事件里的 `x/47` 已经保留了这个信息。

**为什么首次保存不会刷一堆事件**：新字段没有 `HumanReview` 行时，"改前值"取的是**界面当时显示的值**（`_field_rows` 解析出的 `final`），而不是 `None`。所以经理只是点保存、什么都没动，就不会产生任何字段事件。

### 历史接口

`GET /api/review-tasks/{id}` 的 `history` 现在来自事件表，倒序排列，字段扩展为：

```json
{
  "who": "王经理",
  "when": "2026-11-14 15:02",
  "action": "修改「马爹利上一个自然年零售金额(万元)(2025年)」：20 → 26",
  "kind": "change",
  "field": "马爹利上一个自然年零售金额(万元)(2025年)",
  "before": "20",
  "after": "26",
  "reason": "录音里说的是二十六万"
}
```

`kind` 取值：`change` / `reason` / `save` / `submit` / `legacy` / `ai`。前端按 `kind` 上不同颜色，`change` 额外渲染"改前值 → 改后值"两个色块。

排序按 `id` 而不是 `created_at`：SQLite 的 `CURRENT_TIMESTAMP` 只到秒，同一次保存写出的事件会撞在同一秒。

前端同时去掉了两处本地伪造历史（`saveDraft` / `submitReview` 里的 `setHistory`），改成保存后重新拉一次详情。为了不让经理丢失播放位置，`applyDetail` 新增 `keepPlayback` 选项，刷新时保持当前选中的录音而不是跳回第一条。

### 升级与回填

新表由 `create_all` 自动建，不需要 `ALTER TABLE`。但线上已有的 94 条 `human_reviews` 没有对应事件，审核历史会变成空白。

`init_db()` 里加了一段幂等回填：把没有**任何**事件的任务的 `human_reviews` 转成 `legacy` 事件，保留 `final_value` / `change_reason` / `reviewer` / `updated_at`。

```sql
INSERT INTO review_events (task_id, event_type, field_name, value_before, value_after,
                           reason, reviewer, created_at)
SELECT hr.task_id, 'legacy', hr.field_name, NULL, hr.final_value,
       hr.change_reason, hr.reviewer, hr.updated_at
FROM human_reviews hr
WHERE NOT EXISTS (SELECT 1 FROM review_events ev WHERE ev.task_id = hr.task_id);
```

两个刻意的选择：

- 这些行标成 `legacy` 并在界面上写"升级前保存的审核记录"，**不冒充被观测到的历史**。它们的数据是真的，只是没有中间过程。
- 判断粒度是"任务有没有任何事件"，不是"字段有没有"。所以一个已经在升级后被编辑过的任务不会回填——但它第一次保存时，`field_change` 的 `value_before` 就是升级前那个值，信息没丢。

## 顺带修掉的导出 N+1

`GET /api/review-tasks/export` 原来是：

```python
details = [review_task_detail(db, int(task.id)) for task in list_review_tasks(db)]
```

每个任务重查一次任务、再四次 `selectinload`、还要排全部转写片段——而 CSV 只用 13 个字段。任务数一多，查询次数比数据涨得快。

现在走 `export_review_rows(db)`：一次 `_load_tasks`（1 + 4 次 selectinload）+ 内存里构造字段行。查询次数与任务数无关。同时 `_task_response` 支持传入已算好的字段行，避免详情页里 `_field_rows` 被算两遍。

## 已知问题，这轮没动

**已完成的审核仍可被草稿改写。** `save_review` 里：

```python
elif task.status != "completed":
    task.status = "reviewing"
```

也就是说对一个 `completed` 任务保存草稿，数据会变、状态仍是 `completed`、导出内容也跟着变——只是这次**改动会被记录在事件表里**，事后查得到。真要拦，需要引入"重新打开审核"的显式流转（谁打开、为什么、原审核是否作废），属于流程设计，不宜顺手改掉。

## 上线后可以这样查

```sql
-- 某个任务的全部改动，按时间顺序
SELECT id, created_at, event_type, field_name, value_before, value_after, reason, reviewer
FROM review_events WHERE task_id = 12 ORDER BY id;

-- 谁改得最多
SELECT reviewer, COUNT(*) FROM review_events
WHERE event_type = 'field_change' GROUP BY reviewer ORDER BY 2 DESC;

-- 哪些字段最常被人工修正（= AI 最不准 / 业务最关心的字段）
SELECT field_name, COUNT(*) AS edits FROM review_events
WHERE event_type = 'field_change' GROUP BY field_name ORDER BY 2 DESC LIMIT 20;
```

最后一条其实挺有用：它等于免费得到一份"AI 在哪些字段上最不可靠"的排序，可以直接拿去和 `evidence_supports_value` 的失败率对照。
