## 当前结论

本期 MVP 核心框架已完成：支持真实 Excel/录音导入、录音关联、后台 AI 转写与字段提取、确定性状态判断、四模块经理审核、人工修改与原因、草稿/提交及 CSV 导出。当前正式数据库有 5 个批次、9 个任务、5 段录音、505 条转写、188 条 AI 结果和 94 条人工审核记录；2 个任务已完成，1 个待分析，另有 6 个待审核任务。本次又使用最短真实录音在隔离临时数据库完成单店端到端测试；全量 Excel + 全部 8 段录音的批量稳定性仍需最终验收。

2026-11-13 / 2026-11-14 又补了两轮工程化：**接口鉴权、录音访问控制、CSV 注入、上传限额**（安全四项），以及**转写热词、音频规范化、无损切片、幻觉过滤**（识别率四项）。两份独立记录见 `docs/安全加固-2026-11-13.md` 与 `docs/转写准确率-2026-11-14.md`。这两轮都只改动横切关注点，没有动字段提取与状态判定逻辑。

同一天还做了一轮**审核留痕**：新增 append-only 的 `review_events` 表，人工修改不再覆盖写，改前值/改后值/原因/操作人都可回溯；顺带把导出的 N+1 查询去掉。说明见 `docs/审核留痕-2026-11-14.md`。

## 评审建议（2026-11-14 通读发现，逐项排期）

以下是 2026-11-14 通读代码后补充的问题，按优先级排列。已完成的在下方「2026-11-14 审核留痕」一节有实现说明。

- [x] **`HumanReview` 是覆盖写，没有版本历史**：已改为 append-only 的 `review_events` 表，`HumanReview` 保留为"当前值"缓存。见 `docs/审核留痕-2026-11-14.md`。
- [x] **导出是标准 N+1**：`GET /api/review-tasks/export` 原先对每个任务调一次 `review_task_detail`，每次都重查任务并加载全部转写片段。已改走 `export_review_rows`，查询次数与任务数无关。
- [ ] **47 个字段硬编码在业务代码里**（`field_rules.py:20-103`），Excel 模板一改就全线崩，`tests/test_analysis_api.py` 还直接断言 `ai_result_count == 47`，测试是跟着代码改而不是守住需求。建议外置成配置（字段定义 + 单位 + 校验规则），代码只做通用引擎。
- [ ] **数据库迁移靠手写 `ALTER TABLE` 补丁**（`database.py`），第二列变更就会失控，该上 Alembic。本轮新增的 `review_events` 是**新表**，`create_all` 能自动建；补丁逻辑只多了一段幂等回填，没有新增列。
- [ ] **列表接口无分页且计数靠 Python 遍历**（`review_service.py`）：一次查出所有任务 + 四张关联表，每条任务构造 47 个 Pydantic 对象只为数出 4 个状态计数。
  - 注意这不只是加 `limit/offset` 就能解决：前端 `/review` 的搜索、状态筛选、批次筛选、以及"导入顺序"编号全部依赖完整列表在浏览器里算。要改必须同时把筛选下沉到 SQL 并重做列表页分页，属于一次独立的前端改造。
- [ ] **异常被抹平成一句中文**（`analysis_service.py`），分不清 429 限流 / 401 鉴权 / 网络超时，而这三者处理方式完全不同。
- [ ] **前端零测试**，47 字段表格联动、状态机、原因必填全靠手点。
- [ ] **时区靠隐式约定**：模型用 naive `DateTime`，前端假定“无时区即 UTC”再加 8 小时，换 Postgres 或加 `timezone=True` 会静默错 8 小时。
- [ ] **`analysis_service.py` 857 行**同时负责分片、OpenAI 客户端、prompt、三大洋拆分、状态流转、批量调度，建议拆成 `transcribe.py` / `extract.py` / `derive.py` / `orchestrator.py`。
- [ ] **已完成的审核仍可被草稿改写**：`save_review` 里 `elif task.status != "completed"` 意味着 `completed` 任务保存草稿后数据变了、状态仍是 `completed`，导出内容也跟着变。本轮只保证这种改动**会被记录**（事件表里能查到），没有拦。建议改成显式的"重新打开审核"流转。
